## 0. 摘要

1. **流量规模很小，而且几乎全是品牌词**。过去 28 天共 71 次点击、1,286 次展示。品牌导航词（wordbyword 等）带来 41 次点击，占 58%。通用短语 "word by word" 贡献了 59% 的展示，但 CTR 只有 1.7%。前 13 条查询里没有一个功能词，也没有非英语词（F25）。这意味着重构的风险成本低，真正要保护的只有 `/` 这个 URL 和品牌导航词的排名。
2. **非英语关键词不命中，首要原因是架构**。20 个非英语文件（对应 19 种语言）在站内没有任何入链，也没有 sitemap、hreflang 和 canonical，搜索引擎几乎看不到它们（F3、F4、F30）。第二到第四层原因依次是关键词、内容质量和技术。架构不修，后三层的优化对非英语流量几乎不起作用。
3. **内容同时存在"错"和"漏"**：
   - 非英语页上有 8 处配图其实是同一张截图，内容是一篇 VOA 文章，看不出任何功能；另有 60 处图片 404。
   - 至少 10 处文案与产品事实相反，例如"无限 AI 发音""暗色模式""快捷键""不收集个人数据"。
   - Chunks、Action Flow、本地翻译引擎、X 适配这些真实卖点一个都没写（F8、F11）。
4. **页面过重**：单页图片 15.0 MB（英文）/ 17.5 MB（日文、中文）。hero 图是一张 1.69 MB 的 PNG。所有 `<img>` 都没有写宽高，也没有懒加载。移动端 LCP 预计为 Poor（F8、研究 02 §5.4）。
5. **"像 AI 模板站"有四个根因**：没有品牌系统、骨架是通用模板、用了 AI 生成的素材、页面不展示产品本身。最典型的例子：品牌红 #CC3355 在 App 里是主色，也是译文引用条的颜色，网站却用了 iOS 系统蓝（F32、研究 08 §2.3）。
6. **SE 推广不优雅，问题出在"外挂"式实现**。JS 注入固定公告条和紧跟 hero 的整屏卡片，导致主次倒置（手机首屏第一个 App Store 按钮属于 SE）、不分受众（大陆下载不了；8 种语言误写"12 种界面语言"）、爬虫看不到、下载无法归因、两站只有单向链接（F10、研究 04 §4）。新方案按 R40–R43 改为构建期静态的"互补、也值得一试"式推荐：落点精简为 ①②④⑤⑥，zh-Hans 页只留 ②④⑤，WBW 的转化入口优先。
7. **底层的共同根因是没有构建系统**。22 份落地页 HTML 手抄，没有 i18n 源文件（研究 01 §6），由此产生内容漂移、重复页、文案过时和"外挂"推广。
8. **主要约束**：
   - **WBW 定位不变（R39）**：它是"用真实网页学外语的阅读助手"（翻译 + 查词 + 朗读，覆盖多种语言），不是纯翻译工具。
   - 品牌词有歧义，且与 WordByWord.io 撞名（F27）。
   - SE 与 WBW 的功能词高度重叠，须按基线 §B4 与 R39 划分归属：通用的"语言学习 / learn languages by reading"属于 WBW，"学英语"属于 SE（研究 07 §7.2）。
   - 本地化截图只有 en、ja、zh-Hans 三套（F31）。
   - GitHub Pages 不能 301、不能改缓存头（F7）。
   - `/privacy.html` 等契约 URL 必须一直能访问（F12）。
9. **基线（§A–§F）加上裁定 R1–R73，已覆盖本审计全部 P0 和 P1 问题**。每个问题由哪份文档的哪一节解决、受哪些裁定约束，见 §5；问题何时算关闭，见 §6。
10. **最影响本审计置信度的缺口是 H1（GSC 网页、国家维度）和 H2（GA4 基线）**。按裁定第三节：H1 不阻塞，默认用研究 00 基线；H2 须在 M5（T-7 前）导出，否则以上线后前 8 周为基线。

### 1.2 查询结构

### 1.3 对重构风险和收益的含义

| 维度 | 判断 |
|---|---|
| 风险上限 | 【推断】最坏情况是 71 次点击全部丢失。其中 41 次来自品牌导航词，落点是 `/`。基线 §C 已决定 `/` 的 URL 不变；基线 §B1 规定首页主角始终是 WordByWord，R27 又明确：页面 `<h1>` 不含品牌名，但 eyebrow、首段定义句、title 首词必须含 "WordByWord"，logo alt 为 "WordByWord"。真正暴露在风险里的，主要是 "word by word" 带来的 13 次点击。`<h1>` 去掉 "Word by Word" 之后这部分下降属于预期，何况其意图本来就不匹配（观察区间见 §6.3） |
| 旧 URL 迁移的损失 | 【推断】语言页既没有入链也不在 sitemap 里（F4），大概率几乎没有展示，但这一点要靠 H1 证实。如果 `ja-top.html` 等页面实际有展示，301 就必须精确做到单跳（文档 02 §5、文档 06 §3.6.3） |

### 2.4 多语言页是孤岛（S1–S3）【事实】

- 全站唯一指向语言页的链接是 `chrome-extension/index.html:319` → `../zh-top.html`，而 `chrome-extension/` 自己没有任何入链（F4）。
- 26 个非 backup 的 HTML 中，hreflang 和 canonical 都是 0 次（F3）。线上 `robots.txt` 和 `sitemap.xml` 都返回 404。
- 没有语言切换器。logo 链到 `#`，连首页都不链（F4）。
- 旁证（来自非 Google 引擎）：精确搜索 ja、zh、es 页面的原 title，结果只有 `/`（研究 02 §6）。

### 2.5 重复页与低质页（S4、S5）【事实】

- `index.html` 与 `en-top.html` 只差第 185 行的一行注释；`cn-top.html` 与 `zh-top.html` 逐字节相同（F2）。
- `backup/` 下 6 个旧草稿线上返回 200，没有 noindex。内容是"英语学习翻译助手"等早期的英语专属定位，含 41 处相对路径断链，还有 `apps.apple.com/app/yourapp-id` 这样的占位链接（研究 01 §5）。
- `/README.md` 线上返回 200，内部开关说明对外可见（F5）。

### 2.7 性能（T1–T5）

| 页面 | `<img>` 数 | 唯一本地图片 | 图片字节 | 基线 §E 预算 |
|---|---:|---:|---:|---|
| `index.html` | 24 | 17 | **14.97 MB** | 整页 ≤ 1.2 MB，首屏 ≤ 150 KB |
| `ja-top.html` / `zh-top.html` | 20 | 15（含 3 个 404） | **17.52 MB** | 同上 |
| `chrome-extension/index.html` | 14 | 14 | 约 1.1 MB | — |

- T1/T2【事实】`<img>` 全部没有 `width/height` 和 `loading`；没有 `srcset`、`<picture>`、AVIF/WebP（F8）；缓存固定 `max-age=600`（F7）。

## 3. 根因分析

### 3.1 为什么"英语以外的关键词几乎不命中"

```
症状：GSC 前 13 条查询里，非英语词和功能词都是 0（F25）
  ▲  第 1 层 架构 ── 页面没被发现，也没被识别为同一内容的不同语言版本   【首因 RC-S1】
  │  第 2 层 关键词 ── 即使被发现，也匹配不上母语用户的查询            【RC-S2】
  │  第 3 层 内容质量 ── 即使匹配上，也可能不被收录，或者排不上去        【RC-S3】
  │  第 4 层 技术 ── 信号被稀释，页面体验差，放大以上问题              【RC-S4】
  └  外部因素：品牌名本身是英文短语；有同名竞品；部分市场的主流引擎不是 Google
```

**RC-S1 架构（首因）。F30：推断，但证据链完整。**

| 步骤 | 证据 |
|---|---|
| ① 站内只有 1 条链接指向语言页，而发出这条链接的页面本身没有任何入链 | F4 |
| ② 没有 sitemap，也没有 robots | F3 |
| ③ 没有 hreflang/canonical。Google 不靠 `lang` 属性或 URL 判断页面语言，要靠 hreflang 才能把各语言版本归为一组 | F3、F26、研究 02 §2.3 |
| ④ 所以这些页面只能靠外链被发现；即使被收录，也只是互不相关的孤立页。非英语用户搜品牌词时，只会拿到唯一有权重的 `/` | 研究 02 §2.3 推断 |
| ⑤ 实际观察：非 Google 引擎精确搜原 title 只返回 `/`；GSC 中没有非英语查询 | 研究 02 §6、F25 |

结论：架构不修，第 2–4 层做得再好，搜索引擎也看不到（研究 02 §7）。**还需要 H1 证实**：GSC 网页报告中 `*-top.html` 是"未发现"还是"已发现 – 尚未编入索引"。

**RC-S2 关键词（第二因）。**

| 步骤 | 证据 |
|---|---|
| ① 21 个 title 全都是"WordByWord - 泛化的学习助手"；H2 是 "Key Features"、"App Preview" 这类泛称。问题不在"学习"这个定位本身（R39：WBW 定位为学外语的阅读助手，不变），而在于 title 里没有平台词、功能词和产品意图词 | F11、研究 02 §4.2 |
| ② 没有平台词：全站 "iPhone" 出现 0 次。而真实查询普遍带 iphone/app/アプリ/앱 这类修饰 | F11、研究 07 §2.2、§5 |
| ③ 品牌名是一个英文短语，非英语用户不会用母语去搜它；在 ru、de 两个语种，品牌搜索又被 WordByWord.io 的 634 个 URL 占住 | F27 |
| ④ 用了术语，还有误译：alignment/对齐、"посрочное"、"Quét"、"Selecione" | 研究 07 §2.3 |
| ⑤ 定位被写偏："in your browser" 会被理解成浏览器扩展 | F11、C-08 |

结论：即使 RC-S1 修好，如果 title 和页面 H1 还是泛词，页面也只能吃到品牌词的流量。首页主词改为产品/品类意图（R46）。

**RC-S3 内容质量（第三因）。**
- 非英语页有 8 处同图、3 处破图，alt 与图片内容对不上（F8）。
- 正文约 550 词，而且内容过时：还写着 "initial version"，也没有 Chunks、X 适配、本地引擎（F11）。
- 20 个页面的版式、图片、FAQ 完全一样，只换了文字。【推断】这类页面容易被当作模板化的薄内容，落入"已抓取 – 尚未编入索引"（研究 02 §2.4）。

结论：这一层决定页面被收录后能不能排上去。

**RC-S4 技术（第四因，起放大作用）。**
- 重复 URL 没有 canonical（F5）；页面过重，LCP 预计 Poor（F8）；没有 OG 和 JSON-LD，实体识别弱（F3）。
- GitHub Pages 不能做 301（F7）。这在客观上让"改 URL、修架构"一直缺少安全的迁移手段，是 RC-S1 长期没有被修的原因之一。

**外部因素（站点改不了）**
- 中国大陆、韩国、俄罗斯分别以 Baidu、Naver、Yandex 为主（研究 07 §8.2，推断）。
- 没有搜索量数据。
- （B5）Immersive Translate 的 iOS 版已经能在 Safari 里做双语网页翻译（F29），"iPhone 上保留原文的翻译"并不是一片空白。按 R46，这类 how-to 查询只归 Phase 2 的 G1 指南，首页不正面争。

→ **由此确定的设计顺序**：先修架构（文档 02、06），再定关键词（文档 03、08），然后是内容和素材（文档 05、08），最后是技术细节（文档 06）。这与基线 Phase 1 的范围一致。

### 3.2 为什么"看起来像 AI 模板站"

| 根因 | 证据链 | 结论 |
|---|---|---|
| RC-V1 有品牌资产，却没有品牌系统 | App 图标、AccentColor、译文引用条都用 #CC3355（F32）；网站却用系统蓝 #007aff，配 4 个互不相关的强调色，没有任何 token（V4、V8） | 访客从网站上认不出 App 的视觉身份 |
| RC-V2 通用骨架 | 研究 08 模板特征 T1、T4、T6、T7、T8、T9（V6） | 把内容换成任何别的 App 也成立 |
| RC-V3 AI 生成的素材和文案 | ChatGPT 插画图标，文件名都没改；LLM 式的副标题；chrome-extension 子站像 LLM 生成的签名风格（V7、V9） | 识别度高，而且与真实产品无关 |
| RC-V4 页面没有展示产品 | 非英语页的主图是一张空白的 VOA 截图（V1）。产品自己最有辨识度的视觉语汇——红色译文引用条、黄色荧光笔查词、彩色波浪 chunk 下划线——网站上一处都没用（研究 08 §4.3） | 最有差异化的东西，恰恰没有出现。但要按产品语义使用：荧光笔只用于 hero `<h1>` 的一个短语和样张/截图里的查词演示（R65），红色引用条只用于译文和回答 |
| RC-V5 拼贴之后没人维护 | `style.css` 混着三种缩进，只有 2025-06-01 一次提交；规则重复、互相冲突（研究 08 §2.1） | 各处细节不一致，整体显得廉价 |

结论：问题**不是缺素材**，而是有资产没用。研究 08 盘点的素材库比网站实际用到的强得多（研究 08 TL;DR 第 5 条）。所以按基线 §E，只用现有素材就能解决。

### 3.3 为什么当前的 SE 推广"不优雅"

"优雅"的标准（基线 §B1、§F；研究 04 §7.1；按 R40–R43 修订）：
1. WBW 是唯一主角，转化入口优先（R43）。
2. 面向学英语的访客，以"互补、也值得一试"的方式呈现：不做"可能更适合你"一类替换性推荐，也不暗示 WBW 是旧版或将被取代（R40）。
3. 文案符合 SE 事实，卖点只用 WBW 没有的东西（R41）。
4. 静态 HTML 可抓取。
5. 可测量。
6. 双向链接。

现状六项全不达标（P1–P10），根因有四个：

1. **没有模板系统，推广只能外挂**。站点是 22 份手抄 HTML，要全站加一个区块，最省事的办法就是写一段 JS 在运行时注入。注入就意味着要用 relayout 去补偿 fixed header，与 DOM 结构强耦合，产生 CLS，爬虫也看不到（P5、P6）。
2. **没有划分关键词归属，推广反而冲淡了 WBW 的主题**。SE 1.3 之后主打的"逐句译文在原文下方 + 双击语境释义"，和 WBW 自己的核心卖点几乎一样（研究 04 §5、研究 07 §7.2）。推广卡又把"学英语"的 H2 插在 WBW 自己的功能介绍之前（P1）。新方案中 SE 区块的 H2 以 SurfEnglish 品牌开头（R40）。
3. **没有受众模型**。所有语言、所有页面用同一套话术。于是出现了大陆用户下载不了、8 种语言写错界面语言数、对英语母语访客推"学英语"这些问题（P2、P3）。
4. **没有测量闭环，只能靠占据显眼位置来保证曝光**。点击既无法归因到下载，也没有曝光数据，于是"放大位置"成了唯一的手段（P7）。而同一账号下的两款 App 在 App Store 里早已互相展示（F19），网站上本不需要喊得这么大声。

### 3.4 共同的底层根因：没有单一事实源

| 变更类型 | 现在要改几个文件（研究 01 §6.4） | 已经出现的漂移 |
|---|---|---|
| 改一句 FAQ 或加一个功能 | 22 个 HTML，再逐语言翻译 | 所有语言的 FAQ Q4 都还写着 "initial version" |
| 改 GA 配置或加 meta | 26 个 HTML | hreflang、canonical、OG 全站都是 0 |
| 改页脚或年份 | 23 个 HTML | © 2025；ja/it/ko/pt/vi 的页脚各不相同 |
| 加一种语言 | 复制 HTML，再改 2 个 JS 映射 | `cn-top` 和 `zh-top` 两份重复维护 |

这四条根因（3.1 的 RC-S4、3.2 的 RC-V5、3.3 的第 1 条，以及本节）都指向同一个解法：基线 §D 的生成器，即 `build.mjs` 加 `src/locales/*.json` 加模板（文档 06 §3–§5）。

## 4. 机会与约束

### 4.1 品牌词歧义与撞名（B1–B3，F27）

| 实体 | 与 WBW 的冲突 |
|---|---|
| 通用短语 "word by word" | autocomplete 被 Quran、Bible、meaning、词典图书占满；GSC 中展示多但 CTR 只有 1.7%（研究 07 §3.1） |
| WordByWord.io | 同名，做 Chrome 扩展和词汇平台，sitemap 有 634 个 URL（en/ru/de）；它在 Chrome 商店的扩展叫 "WordByWord – Vocabulary Highlighter"。搜索摘要里已经出现把两者写成同一个产品的情况（研究 07 §3.1） |
| Word by Word: Vocabulary Diary | 出现在 WBW 自己 App Store 页的推荐位里 |
| Quran Word by Word 系列 App、*Word by Word* 系列图书 | 占据 "word by word translation (app)" 的搜索结果 |

含义：
- 【决策】保留 `/`（基线 §C）。品牌由 title 首词、eyebrow、首段定义句和 logo alt 承载，页面 `<h1>` 不含品牌名（R27）。"与 WordByWord.io 无关"的声明只放 `/about/` 与扩展页（R15）。署名 "Jinlong"，JSON-LD `alternateName: "Chi Jinlong"`，两站共用 Person `@id: https://surfenglish.app/about/#maker`（U4、R17）。
- 【决策】不优化 "word by word" 头部词，只承接 "word by word translation app" 类长尾（基线 §B4）。v1.0 中"把 H1 统一为连写 WordByWord"的建议**已被 R27 取代**：H1 不放品牌名，凡出现品牌的位置一律写连写的 "WordByWord"。
- 各本地化 App 名（"WordByWord Translate"、"WordByWord翻譯"、"WordByWord Переводчик"，F17）作为 JSON-LD `alternateName`（交给文档 03 §5）。
- WBW 扩展 "WordByWord Translate" 未上架（F20），Chrome 商店里能搜到的同名扩展属于 WordByWord.io。扩展导航入口已由 R2 裁定：S0 态隐藏 header 入口、页面 noindex；S0 态 FAQ 不写扩展名称（R45）。

### 4.2 SE 与 WBW 的关键词重叠（B4，研究 07 §7.2）

| 词簇 | WBW 现在用在哪里 | SE 是否已占（研究 07 §7.1） | 归属（基线 §B4、R39） |
|---|---|---|---|
| 逐句对照 / sentence by sentence / 対訳 | WBW 的 H3、FAQ、ja 页 | 已占（meta.keywords） | 共享，**必须加限定词**：WBW 写"网页 + 任意语言" |
| 双击查词 / 语境释义 / 文脈 | H3 | 已占 | 共享，加限定词 |
| 通用语言学习 / learn languages by reading / 外語学習 / 外语学习 | 没有 | 不占 | **WBW**（R39）：可进 title 后半、description、页面 H1 副句；WBW 定位为"用真实网页学外语的阅读助手" |
| 学英语 / learn English / 英語学習 | WBW 自己没有用，是推广卡注入进来的 | SE 的核心 | **SE 独占**；WBW 的 title、页面 H1、description 不以它为主词（seoLint 同时检查 SE 区块 H2，R40） |
| 新闻 / 分级 / 语块 / 游戏 / 多读 | 没有 | 已占 | SE 独占。WBW 正文可以如实介绍 Chunks（仅英语源文），但不拿"语块"作主关键词 |

| 多语言 / 非英语源语言 | "20 language pairs"（写错了，C-07） | 不占（SE 只教英语，F18） | WBW 独占，但要写清中日韩源文的限制（F15） |
| word by word translation（长尾） | 没有 | 不占 | WBW |

难点【推断】：SE 建在 WBW 的引擎之上，英语场景下两者的核心手势（右滑翻译、双击查词）相同（研究 05 TL;DR 第 4 条）。研究 05 把 SE 称为学英语者的"超集"，但这**不等于 SE 可以替代 WBW**：英语恰恰是 WBW 最核心的场景（默认源语言是英语，Chunks 和 Action Flow 只支持英语），而 WBW 让人读**任何自己想读的网页和帖子**（PRO-01、R39）。因此推荐只能以"互补、也值得一试"的方式出现（R40），回答"我已经有 WBW 了，为什么还要 SE"时，答案只能落在 SE 有、WBW 没有、且不贬低 WBW 的东西上（R41）：

- A1–C1 分级的每日英语新闻信息流；
- 复习小游戏（Sentence Builder / Word Raid）；
- 从 Safari 分享文章进 App（须先核实 SE 分享扩展确实存在）。

语块和端侧/离线语音**不能**当作 SE 的独有卖点：WBW 也有 Chunks，WBW 的 Local Read 同样是端侧 iOS 语音（R41）。具体文案交给文档 04 §5、文档 08。

### 4.4 托管与工程约束
